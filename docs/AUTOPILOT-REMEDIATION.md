# Autopilot dependency remediation

## Execution contract

1. The report finding IDs select the remediation scope. Gemini receives redacted advisory IDs, affected intervals, installed/resolved versions, manifest constraints, lockfile format, and relevant graph locations. Raw lockfiles are excluded from inference.
2. Gemini returns dependency intent (`dependency_proposals`) and/or exact manifest edits. The deterministic fallback produces the same intent. Neither provider supplies authoritative registry facts or lockfile edits.
3. Guardian applies the manifest intent in memory, verifies published npm metadata, and constructs the changed dependency closure. Existing satisfying resolutions are reused; conflicting dependencies are nested under their declaring package. No npm installation, lifecycle hook, source command, or uploaded code executes. Only Guardian's installed semver library evaluates npm ranges.
4. The final gate validates JSON, matching root declarations, nearest-node dependency/peer resolution, published package identity, tarball URL, authentic integrity (or SRI converted from a published SHA-1 shasum), new-release dependency declarations, v2 legacy entries, and advisory status. It checks the actual resolved versions rather than treating a manifest range's lower bound as the installed version. Every changed resolved package must be published and checked against OSV. Advisory matching uses exact package identity.
5. A direct dependency stays on its installed major line if a verified safe fix exists there. A necessary higher major is disclosed as a compatibility risk. Major downgrades are blocked. The planner checks all known advisories for that package, including unselected findings.
6. Each file has one canonical change, one original SHA-256, one final SHA-256, ordered exact anchors, and a reviewable unified diff. Browser application verifies the baseline, saves IndexedDB backups, and journals writes/rollback. Server-assigned `edit_source=npm_registry` permits the same deterministic npm lockfile patch through GitHub preflight; model-authored lockfile patches remain forbidden.
7. Approval and applied/verified lifecycle updates reject unverified or invalid plans. A rescan snapshot must match the plan's final hashes. Verification matches advisories by package name and advisory ID across version/title changes. Partial intelligence triggers an exact-version check for the targeted package; unavailable intelligence cannot prove resolution. Verified local plans can still be undone and reapplied using the original backup and plan ID.

`VERIFIED` means these deterministic dependency invariants passed, not that an AI has certified a package safe or that API compatibility is guaranteed. `UNVERIFIED` means registry/advisory information, published distribution metadata, or the configured resolution budget was insufficient. `REJECTED` means a concrete invariant failed. Both block approval/application. Failed anchors or malformed JSON reject the plan instead of silently dropping edits and certifying the remainder.

The supported automatic dependency path is a root npm `package.json` with an existing lockfile v2/v3. Workspace/override/bundled dependency semantics, dependency removals, non-registry dependencies, unsupported lock formats, and standalone transitive upgrades requiring a parent/constraint change require manual resolution. Incompatible peers remain blocked. No distribution URL or integrity hash is invented. Existing engine budgets are unchanged; remediation metadata uses the existing npm metadata-resolution limits, independently of source-inspection limits. Metadata caches are local to a plan/verification request, so outages and stale advisory results are not retained across plans.

## Reproduced failures

`test_v2_duplicate_dist_metadata_is_updated_atomically` reproduced the original builder failure before the fix. Input: an npm v2 lock with both `packages['node_modules/axios']` and `dependencies.axios` containing the same 1.7.9 distribution URL/integrity; intent: a mocked published 1.8.2 release and matching manifest constraint. The old regex builder updated version fields but skipped the duplicated `resolved` and `integrity` anchors because their occurrence count was two. Validation then correctly returned three failures: the old tarball URL differed from registry metadata, the old packages-graph integrity differed, and the v2 legacy integrity differed. JSON-path construction now updates both records in a single original-content anchor. The regression covers formatted and compact JSON.

Other reproduced failures were ignored structured-only dependency proposals (a verified empty plan), multiple changes for one file with conflicting original/final hash contracts, numeric prerelease comparison and open-ended OSV intervals, GitHub's blanket rejection of deterministic lock edits, and Undo being impossible after the plan became `verified`.

## Verification

Run `.venv/bin/python -m pytest backend/tests -q`, `npm test`, `npm run typecheck`, and `npm run build`.

`backend/tests/test_remediation_pipeline.py` adds external-data-mocked regressions and exercises the actual project scan and remediation APIs with both deterministic and mocked Gemini proposals. It sends the generated plan through `lib/fs-access.ts` using the existing in-memory browser File System Access/IndexedDB test harness, checks apply/Undo/reapply hashes, rescans the resulting files through the real parser/scanner, verifies advisory resolution, and confirms Undo restores the original vulnerable files. GitHub preflight is tested with mocked GitHub responses. These tests do not make live Gemini, registry, advisory, or GitHub calls.

The P0 demo failure was reproduced from the saved 35-finding report: the last advisories had no enrichment data, causing every candidate to be excluded. Missing details are now hydrated once per package from OSV exact-version records, and repeated findings retain all IDs while sharing resolution work. npm requests use the analysis RegistrySession, with published version objects cached from the packument. Dependency-only requests bypass Gemini version selection. Obsolete transitive resolutions are removed when the upgraded parent no longer reaches them.

Browser generation submits `POST /api/scans/{scan_id}/remediation/jobs` and polls `GET /api/remediation/jobs/{id}`. The initial request returns 202; queued/running states remain visible until the complete plan or a specific failure is returned. This keeps metadata resolution out of Next's 30-second rewrite connection. Jobs share the existing two-worker capacity with scans, retain at most 100 states, and enforce report/session authorization when submitted and polled. The synchronous plan endpoint remains available for existing API consumers. Restarting the backend expires in-memory job IDs, producing an explicit 404 message rather than a silent hang.
